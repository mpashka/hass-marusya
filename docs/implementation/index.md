# Как устроена интеграция `marusya_diy`

Родитель: [`../index.md`](../index.md). Внешние контракты — [`../external/`](../external/index.md),
обещания — [`../specification/`](../specification/index.md).

## Назначение и граница

Держит сессии аккаунтов Маруси и кабинета DIY и по описанию устройств поддерживает у каждого
аккаунта привязанную актуальную конфигурацию DIY. Не генерирует описание устройств из
пространств и не знает про ansible: описание приходит параметром записи.

## Части

[`structure.puml`](structure.puml):

| Часть | Модуль | Что делает | Тег |
|---|---|---|---|
| Клиент Маруси | `api.py` | вход по токену VK, провайдеры, `unlink`, начало `link`, устройства | `@tag:marusya-api` |
| Клиент кабинета | `cabinet.py` | список, загрузка, удаление, выбор конфигурации при привязке | `@tag:cabinet` |
| Разбор входа | `vk_login.py` | вставленный адрес `blank.html` → токен VK (оба вида) | `@tag:vk-login` |
| Сборщик YAML | `diy_yaml.py` | описание устройств + адрес + токен → текст конфигурации; проверка описания | `@tag:diy-sync` |
| Токен хуков | `hook_token.py` | служебный пользователь и долгосрочный токен записи; отзыв | `@tag:hook-token` |
| Синхронизатор | `sync.py` | «сравнить → загрузить → перепривязать → удалить прежнюю», откат | `@tag:diy-sync` |
| Записи и формы | `config_flow.py`, `__init__.py` | config flow двух видов записей, options flow, reauth; при удалении записи — отзыв токена и снятие своей привязки | — |
| Работа записей | `runtime.py` | сессия кабинета записи; состояние аккаунта, запуск синхронизации по одной, перевод отказов в состояние и reauth | `@tag:diy-sync` |
| Состояние | `sensor.py` | сущность «Состояние DIY» на записи аккаунта | `@tag:diy-sync` |

Зависимости направлены вниз: синхронизатор знает клиентов и сборщик; клиенты не знают друг
друга и Home Assistant — это обёртки над `aiohttp`, тестируются без Home Assistant.

## Записи

Два вида записей одного домена, различаются полем `kind` в данных:

- **Аккаунт колонки** (`kind: account`, `unique_id` — id пользователя VK). Данные: `device_id`,
  `session_id`, `session_secret`, `account_id`, `vk_user_id`, токен хуков (`hook_token`,
  `hook_refresh_token_id`, `hook_user_id`), привязанная конфигурация (`config_id`,
  `config_name`, `config_fingerprint`). Параметры — описание устройств.
- **Сессия кабинета** (`kind: cabinet`, `unique_id` — `cabinet`, одна на установку). Данные:
  `sh_data`, дата ввода.

## Жизненный цикл аккаунта

[`account-states.puml`](account-states.puml). Состояние — это состояние сущности «Состояние
DIY»; причина отказа — её атрибут, словами и с шагом.

## Синхронизация

[`sync.puml`](sync.puml). Запускается при загрузке записи (в том числе после смены параметров) и
при появлении или обновлении записи кабинета. Сравнивает отпечаток — `sha256` текста
конфигурации — с `config_fingerprint`; совпал и конфигурация в кабинете есть — ничего не делает.
Синхронизации одного аккаунта идут по одной (замок на запись), разные аккаунты — независимо,
кабинет общий и терпит параллельные запросы (каждый клиент держит свою `_csrf_token`).

## Решения

1. **Хуки собирает интеграция, и токен для них заводит она же** — варианты: скрипт присылает
   готовый YAML с токеном (так делал ansible-генератор); Home Assistant читает YAML из файла,
   который положил скрипт. Выбрано: скрипт присылает описание без секретов. Причины: токен не
   ходит через REST и не оседает в истории вызовов служб, не лежит лишним файлом, отзывается
   удалением записи; человек в форме «Настроить» правит то же, что скрипт. Цена — формат
   описания устройств стал контрактом интеграции ([`../specification/devices.md`](../specification/devices.md)).
2. **Кабинет — отдельная запись, а не поле каждого аккаунта.** Сессия одна на все аккаунты и
   живёт 13 месяцев; повторный ввод — одна повторная настройка вместо N. Подзаписи Home
   Assistant (config subentries) не взяты: у них нет reauth, а истечение — главный сценарий
   обеих сессий.
3. **Загрузка — файлом с именем, а не полем `yaml`.** Путь файлом проверен живьём и даёт
   конфигурации предсказуемое имя `hass-<заголовок записи>.yaml`; имя при поле `yaml` не проверено.
   Приставка `hass-` отделяет наши конфигурации от загруженных руками: чистка по имени трогает
   только свои.
   Файл собирается в памяти, на диск не пишется.
4. **Интерфейс синхронизатора — одна операция `async_sync(entry, force=False)`.** Сравнивались:
   отдельные службы «загрузить / привязать / удалить» (гибче, но порядок и откат переезжают к
   вызывающему) и чтение описания из файла (удобно скрипту, но второй источник правды рядом с
   параметрами записи). Одна операция держит порядок и откат внутри — все будущие изменения
   протокола меняют один модуль.
5. **Порядок «загрузить новую → отвязать → привязать новую → удалить прежнюю».** `link` у
   привязанного аккаунта отвечает `409`, поэтому отвязка обязательна; прежняя конфигурация
   удаляется последней, чтобы при отказе привязки было к чему вернуться.
6. **Чужую привязку интеграция не снимает.** Аккаунт без описания устройств, ещё ни разу не
   синхронизированный, остаётся с тем DIY, что был привязан руками; удаление записи снимает
   привязку, только если её ставила интеграция. Иначе добавление аккаунта до описания устройств
   отключало бы колонку.
